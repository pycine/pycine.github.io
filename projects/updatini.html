01Overview

Updates that can’t brick the fleet.

Updatini is a complete over-the-air update path for Yocto-based devices. It combines meta-updatini, a Yocto layer that integrates RAUC A/B updates, with a device agent and a serverless control plane on Cloudflare. The project was built for Raspberry Pi targets around a simple rule: an update should never be able to brick a device or execute untrusted code.

RAUC provides the bottom half of that guarantee: the running system is never overwritten, and a failed boot can fall back to the previous slot. The rest of the project supplies the fleet plumbing around it — device identity, first-boot registration, authenticated polling, targeted releases, and an admin portal that publishes signed bundles.

The result is a small, deployable update system that can authenticate devices, deliver only signed artifacts, and recover from failure without a technician.

02Build

What I built

  • Built meta-updatini, a Yocto layer that integrates RAUC A/B updates into the image build.
  • Built a device agent for first-boot self-registration, authenticated polling, signed-bundle installation, and automatic rollback.
  • Designed a defense-in-depth trust model: device authentication to the server plus RAUC signature verification before install.
  • Developed a serverless backend on Cloudflare — Workers, D1, and R2 — with an admin upload portal that publishes updates and targets specific devices or boards.
  • Validated the failure path: power loss mid-update, corrupted bundle, downgrade attempt, and unauthorized device.
03Architecture

The update path

01

Build

Yocto and meta-updatini produce a signed RAUC bundle for the target board.

02

Publish

The admin portal uploads the bundle to R2, records release metadata in D1, and targets devices or boards.

03

Authenticate

The device agent presents its identity over TLS and polls the Workers API for an applicable release.

04

Verify

The agent downloads the bundle and RAUC verifies its signature before touching the update slots.

05

Install & recover

RAUC writes to the inactive slot. A healthy boot confirms it; a failed boot rolls back automatically.

04Highlights

Technical highlights

A/B by design

RAUC writes to the inactive slot, so the last known-good system stays untouched until the new image proves it can boot.

Defense in depth

Device authentication and bundle signature verification are independent layers. A compromised download channel still cannot produce code execution.

Serverless control plane

Workers handle the API, D1 stores device and release metadata, and R2 stores the bundles. The admin portal publishes and targets releases.

Failure-first validation

Power loss, corrupted artifacts, downgrades, and unauthorized devices were exercised as first-class test cases, not afterthoughts.

05Validation

Failure scenarios, exercised

Validated

Power loss mid-update

The update writes to the inactive slot. Cutting power during installation never touches the running system; the device returns on the known-good slot.

Validated

Corrupted bundle

RAUC verifies the signed bundle before installation. A corrupted or tampered artifact is rejected at the trust boundary.

Validated

Downgrade attempt

The release flow checks the incoming version and refuses an unintended downgrade.

Validated

Unauthorized device

The backend authenticates the device before serving release metadata or artifacts, so an unknown device gets nothing.
